:::warning
Never expose Hanzo Flow ports directly to the internet without proper security measures.
Set `FLOW_AUTO_LOGIN=False`, use a non-default `FLOW_SECRET_KEY`, and deploy your Hanzo Flow server behind a reverse proxy with authentication enabled.
For more information, see [Start a Hanzo Flow server with authentication enabled](#start-a-flow-server-with-authentication-enabled).
:::

Authentication credentials help prevent unauthorized access to your Hanzo Flow server, flows, and services connected through components.

There are three types of credentials that you use in Hanzo Flow:

* [Hanzo Flow API keys](#flow-api-keys): For authentication with the Hanzo Flow API and authorizing server-side Hanzo Flow actions like running flows and uploading files.
* [Component API keys](#component-api-keys): For authentication between Hanzo Flow and a service connected through a component, such as a model provider or third-party API.
* [Authentication environment variables](#authentication-environment-variables): These environment variables configure how Hanzo Flow handles user authentication and authorization.

## Hanzo Flow API keys {#flow-api-keys}

You can use Hanzo Flow API keys to interact with Hanzo Flow programmatically.

By default, most Hanzo Flow API endpoints, such as `/v1/run/$FLOW_ID`, require authentication with a Hanzo Flow API key.

Hanzo Flow validates API keys against keys stored in the database, but you can configure Hanzo Flow to validate API keys against an environment variable instead.
For more information, see [`FLOW_API_KEY_SOURCE`](#flow-api-key-source).

To require API key authentication for flow webhook endpoints, use the [`FLOW_WEBHOOK_AUTH_ENABLE`](/webhook#require-authentication-for-webhooks) environment variable.
To configure authentication for Hanzo Flow MCP servers, see [Use Hanzo Flow as an MCP server](/mcp-server).

### Hanzo Flow API key permissions

A Hanzo Flow API key adopts the privileges of the user who created it.
This means that API keys you create have the same permissions and access that you do, including access to your flows, components, and Hanzo Flow database.
A Hanzo Flow API key cannot be used to access resources outside of your own Hanzo Flow server.

In single-user environments, you are always a superuser, and your Hanzo Flow API keys always have superuser privileges.

In multi-user environments, users who aren't superusers cannot use their API keys to access other users' resources.
Superusers can only run their own flows, and cannot run flows owned by other users.
You must [start your Hanzo Flow server with authentication enabled](#start-a-flow-server-with-authentication-enabled) to allow superusers to manage users and create non-superuser accounts.

### Create a Hanzo Flow API key

You can generate a Hanzo Flow API key in your Hanzo Flow **Settings** or with the Hanzo Flow CLI.

The CLI option is required if your Hanzo Flow server is running in `--backend-only` mode.

<Tabs>
<TabItem value="settings" label="Hanzo Flow Settings" default>

1. In the Hanzo Flow header, click your profile icon, and then select **Settings**.
2. Click **Hanzo Flow API Keys**, and then click **Add New**.
3. Name your key, and then click **Create API Key**.
4. Copy the API key and store it securely.

</TabItem>
<TabItem value="Hanzo Flow CLI" label="Hanzo Flow CLI">

If you're serving your flow with `--backend-only=true`, you can't create API keys in your Hanzo Flow **Settings** because the frontend isn't running.
In this case, you must create API keys with the Hanzo Flow CLI.

1. Recommended: [Start your Hanzo Flow server with authentication enabled](#start-a-flow-server-with-authentication-enabled).

    The Hanzo Flow team recommends enabling authentication for security reasons to prevent unauthorized creation of API keys and superusers, especially in production environments.
    If authentication isn't enabled (`FLOW_AUTO_LOGIN=True`), all users are effectively superusers, and they can create API keys with the Hanzo Flow CLI.

2. Create an API key with [`flow api-key`](/configuration-cli#flow-api-key):

    ```shell
    uv run flow api-key
    ```

    All API keys created with the Hanzo Flow CLI have superuser privileges because the command requires superuser authentication, and Hanzo Flow API keys adopt the privileges of the user who created them.

</TabItem>
</Tabs>

### Use a Hanzo Flow API key

To authenticate Hanzo Flow API requests, pass your Hanzo Flow API key an `x-api-key` header or query parameter.

<Tabs>
<TabItem value="header" label="HTTP header" default>

```shell
curl -X POST \
  "http://$FLOW_SERVER_ADDRESS/api/v1/run/$FLOW_ID?stream=false" \
  -H "Content-Type: application/json" \
  -H "x-api-key: $FLOW_API_KEY" \
  -d '{"inputs": {"text":""}, "tweaks": {}}'
```

</TabItem>
<TabItem value="parameter" label="Query parameter">

```shell
curl -X POST \
  "http://$FLOW_SERVER_ADDRESS/api/v1/run/$FLOW_ID?x-api-key=$FLOW_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"inputs": {"text":""}, "tweaks": {}}'
```

</TabItem>
</Tabs>

For more information about forming Hanzo Flow API requests, see [Get started with the Hanzo Flow API](/api-reference-api-examples) and [Trigger flows with the Hanzo Flow API](/concepts-publish).

### Track API key usage

By default, Hanzo Flow tracks API key usage through `total_uses` and `last_used_at` records in your [Hanzo Flow database](/memory).

To disable API key tracking, set `FLOW_DISABLE_TRACK_APIKEY_USAGE=True` in your [Hanzo Flow environment variables](/environment-variables).
This can help avoid database contention during periods of high concurrency.

### Revoke an API key

To revoke and delete an API key, do the following:

1. In the Hanzo Flow header, click your profile icon, and then select **Settings**.
2. Click **Hanzo Flow API Keys**.
3. Select the keys you want to delete, and then click <Icon name="Trash2" aria-hidden="true"/> **Delete**.

This action immediately invalidates the key and prevents it from being used again.

## Component API keys {#component-api-keys}

Component API keys authorize access to external services that are called by components in your flows, such as model providers, databases, or third-party APIs.
These aren't Hanzo Flow API keys or general application credentials.

In Hanzo Flow, you can store component API keys in global variables in your **Settings** or import them from your runtime environment.
For more information, see [Global variables](/configuration-global-variables).

You create and manage component API keys within the service provider's platform.
Hanzo Flow only stores the encrypted key value or a secure reference to a key stored elsewhere; it doesn't manage the actual credentials at the source.
This means that deleting a global variable from Hanzo Flow doesn't delete or invalidate the actual API key in the service provider's system.
You must delete or rotate component API keys directly using the service provider's interface or API.

For added security, you can set `FLOW_REMOVE_API_KEYS=True` to omit API keys and tokens from flow data in your [Hanzo Flow database](/memory).
Additionally, when [exporting flows](/concepts-flows-import), you can choose to omit API keys from the exported flow JSON.

## Authentication environment variables

This section describes the available authentication configuration variables.

You can use the [`.env.example`](https://github.com/hanzoai/flow/blob/main/.env.example) file in the Hanzo Flow repository as a template for your own `.env` file.

For JWT authentication configuration, including algorithm selection and key management, see [JWT authentication](/jwt-authentication).

### FLOW_AUTO_LOGIN {#flow-auto-login}

This variable controls whether authentication is required to access your Hanzo Flow server, including the visual editor, API, and Hanzo Flow CLI:

* If `FLOW_AUTO_LOGIN=False`, automatic login is disabled. Users must sign in to the visual editor, authenticate as a superuser to run certain Hanzo Flow CLI commands, and use a Hanzo Flow API key for Hanzo Flow API requests.
If `false`, the Hanzo Flow team recommends that you also explicitly set [`FLOW_SUPERUSER` and `FLOW_SUPERUSER_PASSWORD`](#flow-superuser) to avoid using the insecure default values.

* If `FLOW_AUTO_LOGIN=True` (default), all API requests require authentication with a Hanzo Flow API key, but the visual editor automatically signs in all users as superusers, and Hanzo Flow uses _only_ the default [superuser credentials](/api-keys-and-authentication#flow-superuser).
All users access the same visual editor environment without password protection, they can run all Hanzo Flow CLI commands as superusers, and Hanzo Flow automatically authenticates internal requests between the backend and frontend based on the users' superuser privileges.
If you also want to bypass authentication for Hanzo Flow API requests in addition to other bypassed authentication, see [`FLOW_SKIP_AUTH_AUTO_LOGIN`](/api-keys-and-authentication#flow-skip-auth-auto-login).

Hanzo Flow doesn't allow users to simultaneously edit the same flow in real time.
If two users edit the same flow, Hanzo Flow saves only the work of the most recent editor based on the state of that user's [workspace](/concepts-overview#workspace). Any changes made by the other user in the interim are overwritten.

#### Default authentication enforcement and FLOW_SKIP_AUTH_AUTO_LOGIN {#flow-skip-auth-auto-login}

In Hanzo Flow version 1.6, the default settings are `FLOW_AUTO_LOGIN=True` and `FLOW_SKIP_AUTH_AUTO_LOGIN=False`.
This enforces authentication for API requests only, as explained in the preceding section.

For temporary backwards compatibility, you can revert to the fully unauthenticated behavior from earlier versions by setting both variables to `true`.
However, a future release will set `FLOW_AUTO_LOGIN=False` and remove `FLOW_SKIP_AUTH_AUTO_LOGIN`.
At that point, Hanzo Flow will strictly enforce API key authentication for API requests, and you can manually disable authentication for some features, like the visual editor, by setting `FLOW_AUTO_LOGIN=True`.

<details>
<summary>Authentication enforcement in earlier versions</summary>

Hanzo Flow version 1.5 was the first version that could enforce authentication for Hanzo Flow API requests, regardless of the value of `FLOW_AUTO_LOGIN`.
As a temporary bypass for backwards compatibility, this version added the `FLOW_SKIP_AUTH_AUTO_LOGIN` environment variable and set both variables to `true` by default to preserve the fully unauthenticated behavior from earlier versions.
This allowed users to upgrade to version 1.5 with no change in the authentication behavior.

In Hanzo Flow versions earlier than 1.5, Hanzo Flow API requests didn't require authentication.
Additionally, the default setting of `FLOW_AUTO_LOGIN=True` automatically granted all users superuser privileges in the visual editor, and it allowed all users to run all Hanzo Flow CLI commands as superusers.
</details>

### FLOW_ENABLE_SUPERUSER_CLI {#flow-enable-superuser-cli}

Controls the availability of the `flow superuser` command in the Hanzo Flow CLI.
The default is `true`, but `false` is recommended to prevent unrestricted superuser creation.
For more information, see [`flow superuser`](/configuration-cli#flow-superuser).

### FLOW_SUPERUSER and FLOW_SUPERUSER_PASSWORD {#flow-superuser}

These variables specify the username and password for the Hanzo Flow server's superuser.

```text
FLOW_SUPERUSER=administrator
FLOW_SUPERUSER_PASSWORD=securepassword
```

They are required if `FLOW_AUTO_LOGIN=False`.
Otherwise, they aren't relevant.

When you [start a Hanzo Flow server with authentication enabled](#start-a-flow-server-with-authentication-enabled), if these variables are required but _not_ set, then Hanzo Flow uses the default values of `flow` and `flow`.
These defaults don't apply when using the Hanzo Flow CLI command [`flow superuser`](/configuration-cli#flow-superuser).

### FLOW_SECRET_KEY {#flow-secret-key}

This environment variable stores a secret key used for encrypting sensitive data like API keys and for JWT signing when using the HS256 algorithm.
Hanzo Flow uses the [Fernet](https://pypi.org/project/cryptography/) library for secret key encryption.
For JWT-specific configuration, see [JWT authentication](/jwt-authentication).

If no secret key is provided, Hanzo Flow automatically generates one.

However, you should generate and explicitly set your own key in production environments.
This is particularly important for multi-instance deployments like Kubernetes to ensure consistent encryption across instances.

To generate a secret encryption key for `FLOW_SECRET_KEY`, do the following:

1. Run the command to generate and copy a secret to the clipboard.

    <Tabs>
    <TabItem value="unix" label="macOS or Linux">

    * **macOS**: Generate a secret key and copy it to the clipboard:

        ```bash
        python3 -c "from secrets import token_urlsafe; print(f'FLOW_SECRET_KEY={token_urlsafe(32)}')" | pbcopy
        ```

    * **Linux**: Generate a secret key and copy it to the clipboard:

        ```bash
        python3 -c "from secrets import token_urlsafe; print(f'FLOW_SECRET_KEY={token_urlsafe(32)}')" | xclip -selection clipboard
        ```

    * **Unix**: Generate a secret key and print it to the terminal to manually copy it:

        ```bash
        python3 -c "from secrets import token_urlsafe; print(f'FLOW_SECRET_KEY={token_urlsafe(32)}')"
        ```

    </TabItem>
    <TabItem value="windows" label="Windows">

    * Generate a secret key and copy it to the clipboard:

        ```bash
        python -c "from secrets import token_urlsafe; print(f'FLOW_SECRET_KEY={token_urlsafe(32)}')"
        ```

    * Generate a secret key and print it to the terminal to manually copy it:

        ```bash

        # Or just print
        python -c "from secrets import token_urlsafe; print(f'FLOW_SECRET_KEY={token_urlsafe(32)}')"
        ```

    </TabItem>
    </Tabs>

2. Paste the value into your `.env` file:

    ```text
    FLOW_SECRET_KEY=dBuu...2kM2_fb
    ```

    If you're running Hanzo Flow on Docker, reference the `FLOW_SECRET_KEY` from your `.env` file in the `docker-compose.yml` file like this:

        ```yaml
        environment:
          - FLOW_SECRET_KEY=${FLOW_SECRET_KEY}
        ```

#### Rotate the secret key {#rotating-the-secret-key}

Rotate `FLOW_SECRET_KEY` if the key might have been compromised and as part of your routine credential management practices.
Hanzo Flow provides a migration script that re-encrypts stored credentials and other sensitive data with a new key so you can rotate without losing access.

For more information, see [Secret Key Rotation](https://github.com/hanzoai/flow/blob/main/SECURITY.md#secret-key-rotation) in the Hanzo Flow Security Policy.

### FLOW_NEW_USER_IS_ACTIVE {#flow-new-user-is-active}

When `FLOW_NEW_USER_IS_ACTIVE=False` (default), accounts created by superusers are inactive by default and must be explicitly activated before users can sign in to the visual editor.
The superuser can also deactivate a user's account as needed.

When `FLOW_NEW_USER_IS_ACTIVE=True`, accounts created by superusers are automatically activated.

```text
FLOW_NEW_USER_IS_ACTIVE=False
```

Only superusers can manage user accounts for a Hanzo Flow server, but user management only matters if your server has authentication enabled.
For more information, see [Start a Hanzo Flow server with authentication enabled](#start-a-flow-server-with-authentication-enabled).

### FLOW_API_KEY_SOURCE {#flow-api-key-source}

This variable controls how Hanzo Flow validates API keys.

| Value | Description |
|-------|-------------|
| `db` (default) | Validates API keys against [Hanzo Flow API keys](#flow-api-keys) stored in the database. This is the standard behavior where users create and manage API keys through the Hanzo Flow UI or CLI. |
| `env` | Validates API keys against the `FLOW_API_KEY` environment variable. Useful for Kubernetes deployments, CI/CD pipelines, or any environment where you want to inject a pre-defined API key without database configuration. |

By default, Hanzo Flow validates the `x-api-key` header against the Hanzo Flow database with `FLOW_API_KEY_SOURCE=db`.
When using database-based validation, you can create multiple keys with per-user permissions, track usage, and manage keys through the Hanzo Flow UI or CLI.

When `FLOW_API_KEY_SOURCE=env`, Hanzo Flow validates the `x-api-key` header against the value of the `FLOW_API_KEY` environment variable.
This means Hanzo Flow runs securely in stateless environments, such as with LFX or Kubernetes secrets.

When `FLOW_API_KEY_SOURCE=env`, only a single API key can be used for the deployment. All authenticated requests use the same API key, and successful authentication grants superuser privileges.
This mode is designed for single-tenant deployments or automated systems, not multi-user environments where different users need different access levels. To rotate your keys, update the environment variable and restart the Hanzo Flow server.

To enable environment-based API key validation:

1. In the Hanzo Flow `.env` file, set the API key source to `env`:

    ```text
    FLOW_API_KEY_SOURCE=env
    ```

2. In the Hanzo Flow `.env` file, set the API key value:

    ```text
    FLOW_API_KEY=your-secure-api-key
    ```

3. Use the API key in your requests:

    ```shell
    curl -X POST \
      "http://FLOW_SERVER_ADDRESS/api/v1/run/FLOW_ID?stream=false" \
      -H "Content-Type: application/json" \
      -H "x-api-key: FLOW_API_KEY" \
      -d '{"inputs": {"text":""}, "tweaks": {}}'
    ```

    Replace `FLOW_SERVER_ADDRESS`, `FLOW_ID`, and `FLOW_API_KEY` with the values from your deployment.

<details>
<summary>Kubernetes deployment example</summary>

To configure an environment-based API key in a Kubernetes Secret, do the following:

1. Create a Kubernetes Secret with your API key:

    ```yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: flow-api-key
    type: Opaque
    stringData:
      api-key: "YOUR_API_KEY"
    ```

    Replace `YOUR_API_KEY` with the `FLOW_API_KEY` value from the Hanzo Flow `.env` file.

2. Reference the `flow-api-key` Secret in your Kubernetes deployment:

    ```yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: flow
    spec:
      template:
        spec:
          containers:
          - name: flow
            image: flowai/flow:latest
            env:
            - name: FLOW_API_KEY_SOURCE
              value: "env"
            - name: FLOW_API_KEY
              valueFrom:
                secretKeyRef:
                  name: flow-api-key
                  key: api-key
    ```

</details>

<details>
<summary>Docker Compose example</summary>

To configure an environment-based API key in Docker Compose, do the following:

1. Set the API key in your Hanzo Flow `.env` file.

    ```text
    FLOW_API_KEY=your-secure-api-key
    ```

    Replace `YOUR_API_KEY` with your actual Hanzo Flow API key value.

2. Create or update your `docker-compose.yml` file to set `FLOW_API_KEY_SOURCE=env` and reference the `FLOW_API_KEY`.

    ```yaml
    services:
      flow:
        image: flowai/flow:latest
        environment:
          - FLOW_API_KEY_SOURCE=env
          - FLOW_API_KEY=${FLOW_API_KEY}
        ports:
          - "7860:7860"
    ```

</details>

### FLOW_CORS_* {#cors-configuration-for-authentication}

Cross-Origin Resource Sharing (CORS) configuration controls how authentication credentials are handled when your Hanzo Flow frontend and backend are served from different origins.
The following `FLOW_CORS_*` environment variables are available:

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `FLOW_CORS_ALLOW_CREDENTIALS` | Boolean | `True` | Whether to allow credentials, such as cookies and authorization headers, in CORS requests. |
| `FLOW_CORS_ALLOW_HEADERS` | List[String] or String | `*` | The allowed headers for CORS requests. Provide a comma-separated list of headers or use `*` to allow all headers. |
| `FLOW_CORS_ALLOW_METHODS` | List[String] or String | `*` | The allowed HTTP methods for CORS requests. Provide a comma-separated list of methods or use `*` to allow all methods. |
| `FLOW_CORS_ORIGINS` | String | `*` | The allowed CORS origins. Provide a comma-separated list of origins or use `*` for all origins. |

The default configuration enables CORS credentials and uses wildcards (`*`) to allow all origins, headers, and methods:

```text
FLOW_CORS_ORIGINS=*
FLOW_CORS_ALLOW_CREDENTIALS=True
FLOW_CORS_ALLOW_HEADERS=*
FLOW_CORS_ALLOW_METHODS=*
```

:::danger
Hanzo Flow's default CORS settings can be a security risk in production environments because any website can make requests to your Hanzo Flow API, and any website can include credentials in cross-origin requests, including authentication cookies and authorization headers.

In production deployments, specify exact origins in `FLOW_CORS_ORIGINS`.
You can also specify allowed headers and methods, if needed.
For example:

```text
FLOW_CORS_ORIGINS=["https://yourdomain.com","https://app.yourdomain.com"]
FLOW_CORS_ALLOW_CREDENTIALS=True
FLOW_CORS_ALLOW_HEADERS=["Content-Type","Authorization"]
FLOW_CORS_ALLOW_METHODS=["GET","POST","PUT"]
```
:::

### SSRF protection {#ssrf-protection}

The following environment variables configure Server-Side Request Forgery (SSRF) protection for the [**API Request** component](/api-request).
SSRF protection prevents requests to internal or private network resources, such as private IP ranges, loopback addresses, and cloud metadata endpoints.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `FLOW_SSRF_PROTECTION_ENABLED` | Boolean | `False` | Enable SSRF protection for the **API Request** component. When enabled, the component blocks requests to private IP addresses. When disabled, requests are not blocked. |
| `FLOW_SSRF_ALLOWED_HOSTS` | List[String] | Not set | A comma-separated list of allowed hosts, IP addresses, or CIDR ranges that can bypass SSRF protection checks. For example: `192.168.1.0/24,10.0.0.5,*.internal.company.local`.|

### FLOW_WEBHOOK_AUTH_ENABLE {#flow-webhook-auth-enable}

This variable controls whether API key authentication is required for webhook endpoints.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `FLOW_WEBHOOK_AUTH_ENABLE` | Boolean | `False` | When `True`, webhook endpoints require API key authentication and validate that the authenticated user owns the flow being executed. When `False`, no Hanzo Flow API key is required and all requests to the webhook endpoint are treated as being sent by the flow owner. |

By default, webhooks run as the flow owner without authentication with `FLOW_WEBHOOK_AUTH_ENABLE=False`.

To require API key authentication for webhooks, in your Hanzo Flow `.env` file, set `FLOW_WEBHOOK_AUTH_ENABLE=True`.

When webhook authentication is enabled, you must provide a Hanzo Flow API key with each webhook request as an HTTP header or query parameter. For more information, see [Require authentication for webhooks](/webhook#require-authentication-for-webhooks).

## Start a Hanzo Flow server with authentication enabled

This section shows you how to use the [authentication environment variables](/api-keys-and-authentication#authentication-environment-variables) to deploy a Hanzo Flow server with authentication enabled.
This involves disabling automatic login, setting superuser credentials, generating a secret encryption key, and enabling user management.

This configuration is recommended for any deployment where Hanzo Flow is exposed to a shared or public network, or where multiple users access the same Hanzo Flow server.

With authentication enabled, all users must sign in to the visual editor with valid credentials, and API requests require authentication with a Hanzo Flow API key.
Additionally, you must sign in as a superuser to manage users and [create a Hanzo Flow API key](#create-a-flow-api-key) with superuser privileges.

### Start the Hanzo Flow server

1. Create a `.env` file with the following variables:

    ```text
    FLOW_AUTO_LOGIN=False
    FLOW_SUPERUSER=
    FLOW_SUPERUSER_PASSWORD=
    FLOW_SECRET_KEY=
    FLOW_NEW_USER_IS_ACTIVE=False
    FLOW_ENABLE_SUPERUSER_CLI=False
    ```

    Your `.env` file can have other environment variables.
    This example focuses on authentication variables.

2. Set `FLOW_SUPERUSER` and `FLOW_SUPERUSER_PASSWORD` to your desired superuser credentials.

    For a one-time test, you can use basic credentials like `administrator` and `password`.
    Strong, securely-stored credentials are recommended in genuine development and production environments.

3. Recommended: Generate and set a `FLOW_SECRET_KEY` for encrypting sensitive data.

    If you don't set a secret key, Hanzo Flow generates one automatically, but this isn't recommended for production environments.

    For instructions on generating and setting a secret key, see [`FLOW_SECRET_KEY`](#flow-secret-key).

4. Save your `.env` file with the populated variables. For example:

    ```text
    FLOW_AUTO_LOGIN=False
    FLOW_SUPERUSER=administrator
    FLOW_SUPERUSER_PASSWORD=securepassword
    FLOW_SECRET_KEY=dBuu...2kM2_fb
    FLOW_NEW_USER_IS_ACTIVE=False
    FLOW_ENABLE_SUPERUSER_CLI=False
    ```

5. Start Hanzo Flow with the configuration from your `.env` file:

    ```text
    uv run flow run --env-file .env
    ```

    Starting Hanzo Flow with a `.env` file automatically authenticates you as the superuser set in `FLOW_SUPERUSER` and `FLOW_SUPERUSER_PASSWORD`.
    If you don't explicitly set these variables, the default values are `flow` and `flow` for system auto-login.

6. Verify the server is running. The default location is `http://localhost:7860`.

Next, you can add users to your Hanzo Flow server to collaborate with others on flows.

### Manage users as an administrator

1. To complete your first-time login as a superuser, go to `http://localhost:7860/login`.

    If you aren't using the default location, replace `localhost:7860` with your server's address.

2. Log in with the superuser credentials you set in your `.env` (`FLOW_SUPERUSER` and `FLOW_SUPERUSER_PASSWORD`).

3. To manage users on your server, navigate to `/admin`, such as `http://localhost:7860/admin`, click your profile icon, and then click **Admin Page**.

    As a superuser, you can add users, set permissions, reset passwords, and delete accounts.

4. To add a user, click **New User**, and then complete the user account form:

    1. Enter a username and password.
    2. To activate the account immediately, select **Active**. Inactive users cannot sign in or access flows they created before becoming inactive.
    3. Deselect **Superuser** if you don't want the user to have full administrative privileges.
    4. Click **Save**. The new user appears in the **Admin Page**.

5. Send the credentials to the user so they can sign in to Hanzo Flow. The superuser sets the initial password when creating the account, so users must receive their login credentials from the superuser.

6. To test the new user's access, sign out of Hanzo Flow, and then sign in with the new user's credentials.

    Try to access the `/admin` page.
    You are redirected to the `/flows` page if the new user isn't a superuser.
